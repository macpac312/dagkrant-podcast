从业者正在对 Anthropic “没人需要 Claude Code 心理模型”的说法进行验证

Anthropic 发布了一篇文章，介绍了 Claude Code 团队目前的代码审查流程——毕竟 Claude 现在已经编写了 Claude Code 自身约 90% 的代码。最引人质疑的不是这个百分比，而是团队声称自己不再需要的东西。

这篇由 Addy Osmani、Morgan Westlee Lunt 和 Qing Wang 共同撰写的文章，是对 Anthropic 此前关于使用内部系统取代 Git 的报道的补充说明。此前，该公司的单体仓库（monorepo）合并变更量从 5 月的每日约 2500 次激增至 9 月的 30000 多次，代码审查系统随即成了下一个出现问题的环节。他们的目标是让大多数拉取请求“在合并过程中最多仅需一人介入（这个人可以是提交者本人），而且不会导致撤销或事件的增加”。

团队中没有人会在脑海中完整地构建一个关于 Claude Code 的思维模型。而且我们认为，也没有人需要这样做。当有人想了解代码库的某一部分时，他们会请 Claude 针对该部分撰写一份说明文档。这只需要几分钟，而且能准确地反映代码的当前状态。

这段话在 Hacker News 上引发了热议，评论者 jonahx 指出了这种模式所牺牲掉的东西：

如果该系统出现故障，例如出现一个无人能查明的关键漏洞，就再也没有人可以求助了。没有谁的脑海中存在一个可供参考的因果模型，没法据此进行缓慢而系统化的调试。新的信任模型是：我们相信 Claude 总能充分地理解该系统，能够调试任何问题，或做出我们可能需要的任何合理改动。

有一个公开记录的案例，在 Anthropic 自身的代码库中验证了解释器的相关声明。今年 8 月，Claude Code 的合作者 Boris Cherny 在评论中回应了一项关于问题自动关闭的长期投诉。该评论的底部标有“由 Claude Code 生成”的字样。该评论称，当问题“一段时间内没有活动且缺少重现所需的信息”时，就会被关闭，并且“不会仅凭计数来决定问题分类”。

该代码库的 issue-lifecycle.ts 文件规定，问题将在闲置十四天后被标记为过期，再过十四天即被关闭，只有获得十个或以上赞的问题才不受此限制。开发者 marcindulak 统计发现，有超过 6000 个问题虽然标注了重现步骤，却仍然因为“长期无活动”而被关闭。该评论中提出的补救措施——通过评论来重新打开问题——被工作流的机制给阻断了，即在问题关闭七天后将其锁定。该元问题目前已被锁定。

该团队写道，“一个 CLI PR 在一夜之间经历了五十多轮审查和修复，直到其提交者叫停”。默认进行更多轮审查反而使情况恶化，因此他们设定了上限。在 r/ClaudeCode 版块中，评论者 ChemicalExcellent463 表示，自己独立得出了相同的结论：在两次修复失败后便主动停止了操作，因为反复失败意味着智能体对代码的理解有误，而非它一直在修改的那行代码有问题。

当我们对审核者反复标记的内容运行 git blame 命令时，发现其中约 59% 的代码自审核者首次审查以来就没变过。审核者极少发现新 Bug，而是每轮都会发现更多的旧 Bug。

这条边界引发了帖子中一个无人解答的问题。Reddit 评论者 Oximy-Naman 询问，低风险是否涵盖作为文档发布的代理指令变更，因为这些变更“可能在不触及应用程序代码的情况下改变代理行为”，但无人回复。该帖子并未为 CLAUDE.md 文件（其审核人员在每次审核时都会加载该文件）分配任何级别。关于合规性，Hacker News 评论者 gaal_dornick 报告称，其 SOC 2 审核人员要求每项变更在投入生产前都必须经过两轮人工审核；该帖子未讨论审计要求。

并非所有人都认为这是鲁莽之举。评论者 cheema33 指出，大型组织中从来没有人掌握完整的模型，因此就现状来说，这是有所改进的；而评论者 markbao 则表示，每月要花费几千美元进行 AI 代码审查，而如果人工审查的话，那会占用工程师高达三分之一的时间。

该系统的部分功能已公开发布。Code Review for Claude Code 功能已经在 Team 和 Enterprise 套餐中全面开放，而安全审查则作为开源的 GitHub Action 来运行，其 README 文件中明确指出：“该功能尚未针对提示符注入攻击进行强化防护，仅应用于审查可信的拉取请求（PR）。”
