Top Story: DeepSeek DeepInfer—Production Inference, Open-Source Boundaries, and the Economics of Cached Tokens

What happened

DeepSeek released DeepInfer, the inference engine behind V4.1 Flash, alongside production-serving details that make the engineering report as important as the code.

The release covers the inference engine and API-processing layer.DeepInfer supports distributed inference, speculative decoding, SWA Bounded Replay, and structured output on NVIDIA and Huawei Ascend platforms. The accompanyingdeepseek-recipecomponent implements production token encoding/decoding and official-API-compatible processing. DeepSeek says future model inference implementations and optimizations will also appear in this repository.@deepseek_ai,@deepseek_ai,announcement translation

The reported production figures are substantial—but describe a heavily cached service.DeepSeek’s engineering report, as summarized and quoted in the supplied posts, reports155 trillion tokens/day from one cluster,96% input-cache hits,400 ms average time to first token, and230 tokens/s generation, reaching300 tokens/s for coding. It also reports$38 revenue per accelerator-hour at off-peak prices. These are first-party production claims, not independently audited measurements.@ZhihuFrontier,@swyx

“Fully open source” does not mean the entire production service is reproducible from this release.Although DeepSeek describes DeepInfer as fully open source, the technical account says theKV-cache management and load-balancing components are not yet fully released, because they remain coupled to internal infrastructure. The engine is open; important service-level orchestration remains a deployment responsibility.@deepseek_ai,@ZhihuFrontier

vLLM supplied the most concrete comparative response.After acknowledging that DeepInfer was initially built primarily on vLLM and released underApache 2.0, the vLLM team reported decode throughputwithin 6% of DeepInfer’s published resultson GB200 under a matched configuration. It also published AgentX results and reproduction recipes, materially qualifying claims that DeepSeek’s efficiency is inaccessible to existing open-source engines.@vllm_project,@vllm_project,reproduction resources

The release triggered two distinct debates:whether DeepSeek has a uniquely strong serving stack, and whether its disclosures demonstrate high inference profitability more generally. The first now has comparative benchmark evidence; the second remains sensitive to workload mix, cache accounting, hardware cost, and which expenses are included.@Tim_Dettmers,@zephyr_z9,@Yuchenj_UW

Architecture: separate stages, schedule compute rather than tokens

DeepInfer’s disclosed architecture separatesvision encoding, prefill, and decode, allowing each stage to scale against its own bottlenecks. The recommended deployment shapes areordinary eight-accelerator machines for prefilland64–128-accelerator supernodes for decode. Decode uses wide expert parallelism to distribute MoE experts while maintaining large effective batches. These are deployment recommendations, not sufficient evidence of the exact hardware composition of DeepSeek’s production cluster.@ZhihuFrontier

The scheduling details explain why a conventional “tokens per batch” comparison can miss substantial differences:

Prefill scheduling estimates attention-compute cost.Work is allocated using estimated compute rather than raw request length alone. Chunk sizes vary to fit a time budget, instead of enforcing one fixed chunk size across heterogeneous requests.@ZhihuFrontier

Prefill routing does not require cache affinity.Because cached prefixes are pooled in shared storage, a request can go to an available worker rather than the worker that previously served its prefix. In a detailed Chinese-language analysis, inference engineer Su Jin Yan highlights this as a particularly useful production design: prefill data-parallel groups balance on “compute tokens,” while shared storage supplies reusable state. The same analysis highlights request bucketing and FIFO scheduling with a runtime estimator.@SuJinYan123

Decode routing balances both running-request count and KV-cache length.Request count approximates scheduling pressure; accumulated KV length captures memory/state pressure that request count alone misses. The engineering commentary describes prefill/decode scaling signals as aggregate compute load for prefill and running requests for decode.@ZhihuFrontier,@SuJinYan123

Expert-parallel load balancing replicates popular experts.Replicas are periodically redistributed to reduce inter-device waiting caused by routing skew. The trade-off is additional HBM consumption against higher throughput, with diminishing returns as replication increases; the useful replication factor is workload-specific.@ZhihuFrontier,@SuJinYan123

CPU scheduling overlaps accelerator execution.Asynchronous scheduling removes idle gaps between decode steps rather than treating host-side orchestration as free.@ZhihuFrontier

One technically notable observation is the apparent absence of tensor parallelism in the disclosed Blackwell configuration. A commentator contrasts this with default vLLM/SGLang recipes and traces the approach back to DeepSeek V3’s H800-era interconnect constraints. That is an interpretation of the configuration—not evidence that tensor parallelism is generally inferior.@nrehiew_

Scale also matters. Su Jin Yan argues that wide expert-parallel prefill needs enough traffic and workers to pay off, and favorspipeline parallelism for small-to-medium deploymentswith only a few prefill workers. The author also notes that layer heterogeneity can complicate pipeline partitioning. This is practitioner judgment, not a benchmark establishing a universal crossover.@SuJinYan123

Cache hierarchy: persistent prefixes and cheap reconstruction of transient state

The cache design is the central connection between the throughput figures, agent workloads, and reported revenue per accelerator.

Persistent block KV lives in a separate 3FS storage cluster with roughly 100 PiB of SSD capacity.Reported retention isthree days for agent trafficandseven days for chatbot traffic. Any prefill worker can retrieve a cached prefix, decoupling cache locality from compute placement and allowing storage and compute to scale independently.@ZhihuFrontier

That retention is useful for agents that repeatedly resend a growing history of instructions, repository content, tool outputs, and previous responses. It also means155T served tokens/day must not be read as 155T newly generated tokens/day: cache hits are part of the service’s token accounting, while newly computed prefill and autoregressive output impose very different costs. The reported 96% input-cache hit rate is therefore essential context for the headline throughput.@ZhihuFrontier,economic workload assumptions

Persistent block cache is loaded asynchronously.Host-to-device transfers overlap layer execution. Su Jin Yan highlights a lower-level implementation detail: fine-grained KV block copies perform poorly through the CUDA copy engine, so the described path usesGDR/RDMA-based transfers, aiming to saturate PCIe bandwidth without occupying SMs. This is a report-derived technical observation, not a separately measured result in the tweet.@SuJinYan123
